01 · Principles
Chrome is brand, content is software

Forest and gold live in the top bar, table headers, and rules. Everything a user reads or edits is neutral and dense.

One primary action per view

Exactly one filled forest button on screen. Everything else is outline or quiet. This alone removes most of the current clutter.

Every page is the same shape

Tabs → sub-nav → rail → header → stat strip → toolbar → work surface. Learn one page, you know thirty.

Nothing decorative is load-bearing

Ornaments, display type, and colour never carry meaning on their own — status is always a label, not just a hue.

03b · Icons

The app currently runs two icon systems side by side: the Material Symbols Sharp webfont (every .nav-icon in the sidebar) and hand-rolled inline .line-icon SVGs (top bar, renderTaskStats()). Keep the inline SVG set; drop the Material Symbols font. It removes a second network request, works offline without a webfont, inherits colour via currentColor, and the existing .line-icon paths already cover most needs.

Drawing rules
Grid — 24×24 viewBox, fill: none, stroke: currentColor.
Stroke — 1.7 at 15–17px, 1.8 at 13–14px, 2.2 for chevrons. Round caps and joins.
Sizes — 17px top bar · 15px page actions · 13px toolbar and chips · 12px chevrons. No other sizes.
Colour — inherits the text beside it. Gold (#B89968) only on forest surfaces; never gold on white.
Where icons are allowed
Yes — top bar utilities (search, alerts, settings), toolbar affordances (sort, columns, filter chevrons), the row-drawer close, inline add rows, and empty-state hints.
No — stat strips, table headers, table cells, buttons with a text label, tab and sub-nav items, rail rows, page titles. If a label says it, an icon doesn't need to repeat it.
Never alone — an icon-only control needs a tooltip and an aria-label; status is never communicated by icon or colour alone.

4 / 8 / 12 / 16 / 24 / 32 / 48 only. No rem fractions, no clamp() gutters.
Page padding is a flat 24px — replacing today's clamp(2.5rem, 8vw, 8.5rem), which threw away up to 230px of table width per page.
Never pin a height in pixels
the single most expensive rule in this project

Page shells and mockup frames set width only — no height, no overflow: hidden. A fixed pixel height cannot track content: it silently crops the last section, and every attempt to guess the right number lands short. Five separate defects across the Dashboard, Guest List, Budget, Payments and Vendors screens came from this one habit.

Corollary: don't put min-height: 0; overflow: hidden on a page's flex body unless something inside genuinely scrolls. The two places that legitimately scroll are the drawer body and a table's own pane.

Corners

Square. 0px on buttons, chips, inputs, cards, pills. Only avatars are round.

Borders

1px hairlines do all the separating. Structure: #E7E1D4. Row lines: #F0EBE0.

Shadows

None on layout. Popovers and menus only: 0 8px 24px rgba(32,54,45,.14).

Control heights

Chips 28px · buttons and inputs 32px · table rows 36px · top bar 52px.

Two levels is the ceiling

Shot Lists (supplier → list) and Share Packets (packet → chapter) earn a second strip; the inner one is marked in gold and carries a label. Nothing gets a third — at that depth the page is two pages wearing one name.

A strip that scrolls means too many sections — except Database Hub, where 24 tables cannot be anything else.

Rows — 36px, 13px text, 9px/12px padding, 1px #F0EBE0 separators. No zebra striping; hover #FAF8F4.
Editing — cells edit in place: click the cell, type, tab. Borders appear on focus only, never at rest.
Drawer — clicking anywhere outside an editable cell opens the 360px row drawer. Modals are reserved for destructive confirms.
Grouping — one group row per phase/category, showing count and completion. Collapsible.
Selection — checkbox column, shift-click ranges, bulk bar appears above the header.
Columns — resizable and hideable; widths persist per table per profile.
Auto-fit — every table toolbar carries an Auto-fit columns control immediately after the Columns chip. It sizes each column to its widest rendered cell, capped so the name column never falls below its 240px floor. It is an action, not a filter: no chevron, no active state, and it never persists — the widths it writes are the same widths a drag would write.
Where the controls live — the three column controls belong to a toolbar, the row with filter chips and a view switcher. A section header is not a toolbar and never carries them: it introduces content, and a control wedged between prose and a switcher reads as neither. A page whose sections are chosen by a tab bar (17b Honeymoon) still needs a toolbar beneath that bar — the tab bar is navigation. Seven pages carry no controls at all because they carry no tables: 3a, 5a, 11c, 15a, 15b, 15c.
One Columns chip — a toolbar shows exactly one, and it states its count: Columns · 8 of 12. A bare “Columns” beside a counted one is a bug, not a variant.
Row height — a three-state control beside Auto-fit: Compact 30px, Default 36px, Tall 44px. Persists per table per profile like column widths. Compact is for scanning 140 guests; Tall is for tables whose cells wrap to two lines.
Overflow — the table scrolls horizontally inside its own pane; the page never scrolls sideways.
Empty — one line of plain text plus the inline add row. No illustrations.
Chip honesty — a filter chip must describe the rows actually rendered. Active (forest border + ✕) means the table IS filtered; if the full grouped table is shown, every chip renders inactive (#D9CFBA border, "…: all", chevron, no ✕).
Column budget — fixed widths must leave the name column ≥ 240px after the drawer is subtracted: frame − rail 224 − padding 48 − borders 2 − drawer 360. Trim the default column set rather than squeezing names; the rest live in the drawer. Guest List shows 6 of 24, Budget itemized 8 of 12.
Group rows — one format everywhere: N items · $X committed · $Y paid · target $Z.
Bars — the track carries overflow: hidden and fills cap at 100%. Over-target reads as a red fill at 100% plus the negative variance figure, never a >100% width.
09 · Print & keepsakes

Print is the one place the editorial voice stays. Screen density serves work; paper serves the client. Two print classes, no more.

Class A
Working documents

Vendor packets, day-of timelines, task lists, guest lists, seating charts. Letter portrait (A4 aware), 12pt minimum, black on white, hairline rules, no gold, no fills. Repeating header: couple, page title, date printed. Footer: page x of y. Tables break at row boundaries; group rows repeat on carry-over pages.

Class B
Keepsakes

Vision & Foundation, Prayer Journal, Premarital Counseling, ceremony programs. Cormorant Garamond returns for headings and Scripture, generous margins (0.9in), a single gold hairline as the only ornament, one accent per page. These are the pages a couple keeps — they should look printed, not exported.

Both classes print from the page itself — no separate print templates to drift out of sync. Screen chrome (tabs, rail, toolbar, drawer, chips) is hidden; the work surface expands to the full measure.

15b · Every token, light and dark

The complete semantic layer. These are the values shipped in redesign/redesign-tokens.css, which reuses the property names the planner already defines in css/planner-tokens.css — so swapping that one file restyles most of the app with no markup edits. The trap that catches everyone, including me. In light mode #20362D is used for both table-header backgrounds and heading text, and #2D4A3E for both the top bar and primary buttons. 17 · Viewer preferences

The only surface that appears on all thirty-seven pages. It hangs off the avatar already in the top bar — not a separate gear icon, which would put two settings affordances within thirty pixels of each other and make users guess. Drawn at size in 16a.

Undo and redo are not in here

They live in the top bar as two icon buttons, because they are high-frequency and low-ceremony — burying a one-click action two clicks deep is a downgrade. The menu carries the keyboard shortcut as a reminder and a link to Planner History, which is the readable log. Fifteen snapshots are kept; the log is view-only except that a row can still be undone while its snapshot is one of those fifteen. Clearing the log lives in Wedding Setup’s danger zone, not on the log itself.

The test

A setting belongs in the avatar menu only if it changes what this viewer sees and changes nothing a share-packet recipient would ever receive. Theme passes. Budget target does not. Anything that fails the test lives on Wedding Setup, which is about the wedding rather than about the app.

Anchor

320px wide, top: 46px; right: 14px — below the top bar, aligned to the avatar it opens from. Height is capped at calc(100% − 60px) with the panel scrolling, so it can never render past the bottom of the window: the six focus presets and the shortcut list overflow a short viewport otherwise.

Geometry

Same vocabulary as everything else: square corners, one hairline between groups, uppercase eyebrows, no shadow inside the panel.

Controls

Segmented rows for 2–3 choices, chips for the six focus presets, one toggle for Preview Mode. No free sliders and no colour picker.

Persistence

Per device, not per planner. A preference never travels in a backup file or a share packet.

Appendix · page inventory

† marks a page that does not exist in the current app — Households and Contacts are derived views over existing records, and Print Centre collects what is now the top-bar print dropdown. All three are approved for build; they are additions to scope, not recreations. Thirty-seven pages, all drawn. Screen ids refer to Planner Screens All — forty-four screens in one document, newest batch first. Planner Screens Dark carries the same forty-four on the §15 ramp, and Planner Prototype builds six of them as working software. Every one uses the §07 frame with no exceptions. One page sits outside the tab rule: Planner History is reached only from the top-bar undo and redo buttons and the avatar menu, so nothing is lit in its tab strip and its sub-nav row says where you came from instead. That is deliberate — a log is somewhere you are sent, not somewhere you browse to. Three entries are reference pages — Get Started, the Page-by-Page Guide and the FAQ — which keep the shell, rail and page header but carry prose on the work surface: no stat strip, no toolbar, no bulk bar, no drawer, because no record is open. Three are derived views rather than tables of their own — Households and Contacts group the guest and vendor records, and both carry a read-only rule in place of an add button for the thing they are named after.
